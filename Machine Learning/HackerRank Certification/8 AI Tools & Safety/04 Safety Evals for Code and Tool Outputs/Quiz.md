## Quiz: Safety Evals for Code and Tool Outputs

Safety Evals for Code and Tool Outputs
Your team uses AI to generate code, scripts, and configuration changes. You need to prevent security regressions, licensing violations, hallucinated APIs, and tool incidents before they reach production.


Why do AI-assisted code changes need dedicated security evals?

Security issues always appear as test failures.

AI increases change volume and predictable unsafe patterns.

Security evals replace code review.

Security evals are only needed after an incident.
Correct Answer!
Dedicated checks catch unsafe patterns that manual review can miss.

Which control best reduces licensing and security risk from dependencies?

Allow any dependency to speed up changes.

Use dependency allowlists and license scanning in CI.

Only scan dependencies after release.

Rely on manual review for all dependency changes.
Correct Answer!
This prevents incompatible or vulnerable dependencies from being added.

What is the most reliable control against hallucinated APIs?

Increase model creativity.

Ground outputs in current docs and verify with compilation/tests.

Only review code visually.

Skip verification to move faster.
Correct Answer!
Grounding plus verification catches nonexistent APIs.

Which is the best example of a security regression test?

A test that checks formatting rules only.

A test that fails if auth middleware is missing on protected routes.

A test that counts how many lines changed.

A test that checks only for syntax errors.
Correct Answer!
This directly prevents a high-impact security regression.

What is the first priority during an AI tool incident?

Write a detailed postmortem.

Contain the blast radius by disabling risky actions.

Increase model temperature to reduce repetition.

Ignore the incident until a customer reports it.
Correct Answer!
Containment prevents further harm while diagnosis proceeds.

Why does AI-assisted development increase licensing risk?

AI outputs are always illegal to use.

AI can generate code without clear provenance, bypassing usual checks.

Licensing only applies to open-source projects.

Licensing is irrelevant for internal tools.
Correct Answer!
Without provenance, license compliance is difficult to prove.

Why should non-code outputs (configs, scripts) be evaluated?

They are low risk compared to code.

They can change security posture and infrastructure behavior.

They do not affect production.

They are always generated by humans.
Correct Answer!
Non-code outputs often define security boundaries.

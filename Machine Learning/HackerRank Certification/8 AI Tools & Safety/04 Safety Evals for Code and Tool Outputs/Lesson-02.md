## When AI Code Looks Too Familiar

Imagine you ask an AI assistant to generate a utility function for parsing configuration files. It produces clean, working code. You review it, merge it, and ship it in your product. Six months later, a developer recognizes the code—it closely matches a GPL-licensed implementation from an open-source project. Your proprietary product now includes code that might violate the GPL license, and you cannot prove where it came from.

This is why licensing is a runtime risk, not just a legal risk. AI-generated code can incorporate patterns or snippets that resemble licensed content. Even if the tool does not copy verbatim, it may produce code that is too close to restricted sources. This is a risk for companies that distribute software or expose code to customers.

In this lesson, you will learn how to prevent licensing and attribution risks in AI-generated code, how to build guardrails that detect problematic patterns, and how to track provenance for code snippets. You will understand why AI workflows increase licensing risk, how to automate compliance checks, and how to balance protection with developer productivity.

By the end, you will have a practical licensing framework that prevents accidental violations while still allowing AI tools to be useful.

Licensing Is a Runtime Risk, Not Just a Legal Risk
The practical problem is not "AI wrote code." The problem is that licensing obligations are often unclear. If you cannot trace the source, you cannot prove compliance. When code resembles licensed content but you cannot prove it is original, you are at risk.

Consider what happens without provenance. An AI assistant generates code that works perfectly. It looks original, but it closely matches a GPL-licensed implementation. You ship it in a proprietary product. Later, someone notices the similarity. You cannot prove the code is original, so you cannot prove compliance. This is a legal risk, but it is also an engineering risk because it affects what you can ship.

License Categories Developers Should Recognize
You do not need to be a lawyer to manage licensing risk, but you should understand basic categories:

Permissive licenses (MIT, Apache 2.0) that allow broad reuse. These are generally safe for most use cases.

Copyleft licenses (GPL) that impose sharing obligations. These require careful handling in proprietary products.

Custom or restricted licenses that limit commercial use. These may prohibit certain uses entirely.

AI-generated code can accidentally resemble code from any of these categories. Your workflow should be able to detect and handle that risk. When you understand license categories, you can make informed decisions. When you do not understand them, you make risky decisions.

Licensing in Internal Versus External Distribution
Internal-only tooling often has more flexibility, but the moment you distribute code or expose it to customers, licensing risk becomes real. If your product includes code generated by AI, you need to be able to prove that dependencies and large snippets are compliant.

Consider the difference. Internal tools that never leave your organization have more flexibility with licensing. But if you ship a product that includes AI-generated code, you need to prove compliance. When distribution is external, compliance is required. When distribution is internal, compliance is still good practice.

Common Licensing Failure Modes
Teams typically run into:

Unattributed code: code that resembles a known licensed project. This happens when AI generates code similar to existing implementations.

Incompatible license mixing: adding dependencies with restrictive licenses. This happens when AI adds dependencies without considering license compatibility.

Untracked third-party snippets: examples copied into production without review. This happens when developers copy examples without checking licenses.

These issues are fixable if you have guardrails in place. When guardrails are present, violations are prevented. When guardrails are missing, violations happen.

Why AI Workflows Increase Licensing Risk
AI tools speed up coding, which can bypass the usual "where did this come from" checks. Developers may assume outputs are safe, and reviewers may focus on correctness rather than license compliance. This is why licensing needs its own evaluation gate.

Consider what happens without licensing gates. Developers use AI tools to generate code quickly. They focus on functionality, not licensing. Reviewers focus on correctness, not compliance. Licensing is forgotten, and violations happen. With licensing gates, compliance is checked automatically, preventing violations.

If you already use an open source policy, AI-assisted development should plug into it rather than bypass it. The tool should not be treated as a special case. It should be treated as another code source that must comply with the same rules. When AI tools follow the same rules as other code sources, compliance is consistent.

Guardrails That Reduce Licensing Risk
Practical guardrails include:

Dependency allowlists: approved licenses only. Block dependencies with incompatible licenses automatically.

Automated license scanners: detect incompatible licenses in dependencies. Scan every dependency change.

Snippet provenance tracking: require source references for large copied blocks. Track where code comes from.

These checks are lightweight and can run in CI. They prevent accidental violations without slowing development. When checks are automatic, compliance is consistent. When checks are manual, compliance is inconsistent.

A Simple License Compatibility Matrix
Many teams maintain a short matrix that maps license types to allowed usage:

Permissive licenses: allowed. These are generally safe for most use cases.

Weak copyleft: allowed with attribution. These require attribution but are generally safe.

Strong copyleft: restricted or prohibited. These require careful handling and may be prohibited.

This matrix does not replace legal review, but it gives engineers a clear default. If a dependency falls outside the matrix, it triggers an explicit review. When matrices are clear, decisions are fast. When matrices are unclear, decisions are slow.

license-scanner-integration.py
```python
#!/usr/bin/env python3
"""
License scanner for AI-assisted dependency changes.
Checks licenses against compatibility matrix.
"""

import subprocess
import json
from typing import List, Dict, Optional
from dataclasses import dataclass

@dataclass
class LicenseCheck:
  """Result of a license check."""
  dependency: str
  license: str
  category: str
  allowed: bool
  requires_attribution: bool
  message: str

class LicenseScanner:
  """Scans dependencies for license compliance."""

  def __init__(self, license_matrix_path: str):
      self.license_matrix = self._load_matrix(license_matrix_path)

  def _load_matrix(self, path: str) -> Dict:
      """Load license compatibility matrix."""
      # In real implementation, load from YAML
      return {
          "permissive": {
              "allowed": True,
              "attribution_required": False,
              "examples": ["MIT", "Apache-2.0", "BSD-2-Clause"]
          },
          "strong_copyleft": {
              "allowed": False,
              "attribution_required": True,
              "examples": ["GPL-2.0", "GPL-3.0", "AGPL-3.0"]
          }
      }

  def scan_dependencies(self, requirements_file: str) -> List[LicenseCheck]:
      """Scan dependencies in requirements file."""
      # Parse requirements file
      dependencies = self._parse_requirements(requirements_file)

      checks = []
      for dep in dependencies:
          license_info = self._get_license_info(dep)
          check = self._check_license(dep, license_info)
          checks.append(check)

      return checks

  def _parse_requirements(self, requirements_file: str) -> List[str]:
      """Parse requirements.txt file."""
      with open(requirements_file, 'r') as f:
          lines = f.readlines()

      dependencies = []
      for line in lines:
          line = line.strip()
          if line and not line.startswith('#'):
              # Extract package name (before == or other operators)
              dep_name = line.split('==')[0].split('>=')[0].split('<=')[0]
              dependencies.append(dep_name.strip())

      return dependencies

  def _get_license_info(self, package: str) -> Optional[Dict]:
      """Get license information for a package."""
      try:
          # Use pip show or package metadata
          result = subprocess.run(
              ['pip', 'show', package],
              capture_output=True,
              text=True
          )

          # Parse license from output
          # In real implementation, use proper package metadata parsing
          return {"license": "MIT", "category": "permissive"}
      except Exception:
          return None

  def _check_license(self, package: str, license_info: Dict) -> LicenseCheck:
      """Check if license is allowed."""
      license_name = license_info.get("license", "Unknown")
      category = self._categorize_license(license_name)

      matrix_entry = self.license_matrix.get(category, {})
      allowed = matrix_entry.get("allowed", False)
      requires_attribution = matrix_entry.get("attribution_required", False)

      if not allowed:
          message = f"License {license_name} ({category}) is not allowed. Requires approval."
      elif requires_attribution:
          message = f"License {license_name} requires attribution."
      else:
          message = f"License {license_name} is allowed."

      return LicenseCheck(
          dependency=package,
          license=license_name,
          category=category,
          allowed=allowed,
          requires_attribution=requires_attribution,
          message=message
      )

  def _categorize_license(self, license_name: str) -> str:
      """Categorize a license based on its name."""
      license_lower = license_name.lower()

      if any(perm in license_lower for perm in ["mit", "apache", "bsd"]):
          return "permissive"
      elif any(gpl in license_lower for gpl in ["gpl", "agpl"]):
          return "strong_copyleft"
      else:
          return "unknown"
```

Consider what happens with similarity checks. An AI assistant generates a large code snippet. A similarity check compares it to known open source code. If similarity is high, the code is flagged for review. This prevents accidental violations before they happen. When checks are in place, violations are prevented. Attribution Policies for AI Outputs
If your policy requires attribution for certain sources, you need a consistent approach:

Require developers to confirm that code is original or derived from approved sources: make provenance explicit.

Document any external references in the PR: keep a record of sources.

Keep an internal record of high-risk outputs for audit: enable compliance verification.

This is not about blaming developers. It is about making provenance explicit. When provenance is explicit, compliance is verifiable. When provenance is implicit, compliance is not verifiable.

When to Require Human Review
Not every change needs a licensing review. High-risk triggers include:

Large chunks of new code without clear provenance: these might resemble licensed content.

New dependencies or major version upgrades: these might introduce incompatible licenses.

Code that resembles known external examples: these might violate attribution requirements.

These triggers can be encoded in review checklists or CI rules to keep the process consistent. When triggers are clear, reviews happen when needed. When triggers are unclear, reviews are skipped.

Common Pitfalls and Solutions
Pitfall: assuming AI output is license-free. Solution: treat AI output like any other third-party code and apply the same checks. When AI output is treated as special, compliance is inconsistent. When AI output is treated like other code, compliance is consistent.

Pitfall: ignoring dependency changes. Solution: require explicit approval for new dependencies and scan licenses in CI. When dependencies are ignored, incompatible licenses are introduced. When dependencies are reviewed, incompatible licenses are prevented.

Pitfall: missing provenance for large snippets. Solution: require source references when code resembles external examples. When provenance is missing, compliance cannot be verified. When provenance is present, compliance can be verified.

Pitfall: no automation. Solution: automate license scanning and dependency checks. When checks are manual, they are skipped. When checks are automatic, they are consistent.

Pitfall: unclear policies. Solution: document license policies clearly. When policies are unclear, decisions are inconsistent. When policies are clear, decisions are consistent.
